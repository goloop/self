# 14. AI у продакшн-формі

**Задача.** Розділ 05 робив виклики; цей - форма, якою реальна служба їх
обгортає. Взято зі служб, що дають користувачу принести власний ключ провайдера,
просять модель щось дослідити й хочуть відповідь у схемі. З'являються три
проблеми, яких немає в одиничному виклику: якого провайдера будувати і чи він
взагалі вміє те, що ви зараз попросите; як деградувати, коли не вміє, без
матчингу англійського тексту помилки; і як спіймати помилку в схемі до того, як
вона стане 400-кою на ключі користувача після деплою.

**Модулі.** [`ai`](https://github.com/goloop/ai) - провайдер-агностичний контракт
- `Client`, `Capabilities`, сентинели і `ValidateStrictSchema` - а пакети
драйверів ([`anthropic`](https://github.com/goloop/anthropic),
[`openai`](https://github.com/goloop/openai) та інші) його реалізують.

**Рецепт.** [`recipes/014-ai-production`](../recipes/014-ai-production/)

Як і рецепт 005, це компілюється й тестується зелено **без API-ключів**: клієнт
будується лише для провайдера, чий ключ присутній, а живий виклик друкує нотатку
й пропускається, коли жодного немає. Робота з можливостями й схемою не потребує
мережі взагалі.

## Приклад A - фабрика

Одна функція мапить ім'я провайдера й ключ на `ai.Client`, тож ніщо інше в коді
не залежить від провайдера:

```go
func newClient(name, key string) (ai.Client, error) {
	switch name {
	case "anthropic":
		return anthropic.New(key), nil
	case "openai":
		return openai.New(key), nil
	default:
		return nil, fmt.Errorf("unknown provider %q", name)
	}
}
```

Реальна служба читає ім'я й ключ з акаунта, тож кожен користувач приносить свого
провайдера - а решта фічі ніколи не знає, якого саме.

## Приклад B - спитати, що воно вміє, до виклику

Чи показувати контрол «пошук у мережі» - рішення, яке ви приймаєте *до* виклику.
Інстинкт - таблиця імен провайдерів; проєкти, з яких це взято, тримали ту
таблицю в трьох місцях - бекенд двічі, фронтенд один раз - і всі три застаріли
того дня, коли драйвер навчився шукати. Питайте драйвер натомість:

```go
if ai.SupportsHosted(client, ai.Hosted{Kind: ai.HostedWebSearch}) {
	// запропонувати контрол
}
hc, _ := ai.HostedCapabilityOf(client, ai.HostedWebSearch)
// hc.WithFormat.JSONSchema каже, чи пошук + схема вміщаються в один виклик
```

`Capabilities` - це **підказка, не дозвіл**: чи запит справді вдасться, все ще
залежить від моделі, акаунта й регіону, тож сентинели з прикладу C лишаються
істиною. Але це правильна підказка для рішення до-виклику - запропонувати фічу і
один запит чи два - а драйвер, що не описує себе, звітує «нічого», а не хибне
«так».

## Приклад C - деградувати на сентинелі, не на тексті

Коли провайдер не вміє того, що попросили, драйвер каже це своїм сентинелем, а
код розгалужується на `errors.Is`:

```go
resp, err := client.Generate(ctx, req) // req просить вебпошук
switch {
case err == nil:
	// використати resp.Citations()
case errors.Is(err, ai.ErrNoHosted):
	// цей провайдер не вміє шукати: відкотитись до звичайної відповіді, або
	// попросити користувача змінити провайдера - не відповідати з пам'яті вдаючи
case errors.Is(err, ai.ErrFormatWithHosted):
	// він не буде шукати ТА забезпечувати схему разом: зробити два виклики -
	// пошук прозою, потім перекласти в схему
default:
	return err
}
```

Це замінило крихкий матчинг повідомлень, який два проєкти написали незалежно -
кожен парсив англійську 400-ки провайдера, щоб угадати, що впало. Драйвер тепер
сам загортає ту 400 в сентинел, тож один `errors.Is` покриває і обмеження,
відоме наперед, і вивчене з дроту; власний `*ai.APIError` провайдера все ще
досяжний через `errors.As`, коли треба деталь.

Форма з двома викликами, яку згадує приклад C - пошук прозою, потім перекладання
в схему - це продакшн-відповідь провайдеру (як Gemini), що забезпечує схему,
обмежуючи вивід, а це не тримається разом із заземленням.
`hc.WithFormat.JSONSchema` з прикладу B каже наперед, яким провайдерам це
потрібно.

## Приклад D - перевірити схему до відправлення

Сувора схема - літерал, повністю відомий до будь-якого виклику. Пропущений запис
у `required` не має бути тим, що провайдер каже вам мережею, на ключі
користувача, після деплою. `ai.ValidateStrictSchema` перевіряє правила суворого
режиму - кожен об'єкт потребує `additionalProperties: false` і кожну властивість
у `required` - і називає шлях до вади:

```go
if err := ai.ValidateStrictSchema(storySchema); err != nil {
	// ai: strict schema is not provider-compatible:
	//   properties.stories.items: "required" is missing "placeLocal"
}
```

Поставте це в тест (рецепт так робить) - і одруківка в схемі стає падінням
збірки, а не продакшн-інцидентом. Вона перевіряє правила, що вирішують, чи
суворий режим прийнято, і нічого про те, чи схема описує задумане - це все ще
ваше.

## Звіт про виконання

```
$ go run .                        # без жодних ключів
A/B. what can each provider be asked for (a hint, before any call):
   anthropic web search=true   search+schema in one call=emulated
   openai    web search=true   search+schema in one call=native
   -> the UI shows the search control only where it is supported
D. strict schema checked locally before any call:
   storySchema is strict-compatible
C. live call: skipped - set ANTHROPIC_API_KEY or OPENAI_API_KEY
   (compile and tests are green without any key)
```

Зверніть увагу на таблицю можливостей вище: `anthropic` звітує `emulated` для
пошук + схема (його структурований вивід емульований у промпті, тож обидва
співіснують, але ніщо не забезпечується), `openai` звітує `native` (його
ендпоінт responses несе формат, тож пошук і сувора схема вміщаються в один
виклик). Це рівно те знання, яке проєкти підтримували руками, тепер прочитане з
драйвера.

## Що ви дізналися

- Фабрика перетворює ім'я провайдера + ключ на `ai.Client`; тримайте решту
  провайдер-агностичною.
- `ai.SupportsHosted` / `ai.HostedCapabilityOf` відповідають до виклику - чи
  пропонувати фічу і чи вона в один запит чи два - замінюючи таблицю імен
  провайдерів, що застаріває. Це підказка, не дозвіл.
- Деградуйте на власних сентинелах драйвера (`ai.ErrNoHosted`, `ai.ErrNoFormat`,
  `ai.ErrFormatWithHosted`) через `errors.Is`, ніколи на тексті 400;
  `*ai.APIError` лишається досяжним через `errors.As`.
- `ai.ValidateStrictSchema` у тесті перетворює помилку в схемі на падіння
  збірки, а не живу 400 на ключі користувача.

Далі: помилки, які все це продукує, у формі, на яку фронтенд може діяти.
