# 11. Вхід, який переживе продакшн

**Задача.** Взяти обробник входу, що працює першого дня, і зробити його
придатним для сотого. Наївна версія падає в продакшні трьома способами, і
жодного з них не видно в розробці: відсутній секрет підпису, який вилазить лише
коли перший користувач намагається увійти; скрипт підбору пароля, що б'є в
ендпоінт тисячу разів на хвилину; і сплеск паралельних спроб, що вичерпує
пам'ять, бо кожна Argon2id-перевірка - вірний пароль чи ні - коштує десятки
мегабайтів за задумом.

**Модулі.** [`env`](https://github.com/goloop/env) читає й валідує конфігурацію,
[`jwt`](https://github.com/goloop/jwt) перевіряє ключ підпису,
[`argon2id`](https://github.com/goloop/argon2id) хешує паролі,
[`auth`](https://github.com/goloop/auth) видає токени й вирівнює таймінг,
[`middlewares`](https://github.com/goloop/middlewares) обмежує частоту й
паралельність, [`mux`](https://github.com/goloop/mux) групує маршрути, а
[`resp`](https://github.com/goloop/resp) відповідає машинним слагом.

**Рецепт.** [`recipes/011-hardened-signin`](../recipes/011-hardened-signin/)

Це перший розділ Частини IV, яка будує патерни, а не вводить модулі. Кожен узято
зі служб, що ганяють увесь стек GoLoop у продакшні, і кожен рецепт - повна
програма, яку можна запустити.

## Патерн

Чотири гальма перед однією дорогою операцією, саме в цьому порядку:

1. **Падати на старті, а не на першому вході.** Відсутній чи слабкий секрет
   підпису - помилка конфігурації. Спіймана на старті, вона - відкочений деплой;
   спіймана на першому вході, вона - аварія.
2. **Обмежити частоту підбирача.** Бюджет на адресу за вікно спиняє скрипт від
   мільйонів паролів і ніколи не заважає людині, що кілька разів помилилась.
3. **Скинути сплеск.** Обмеження паралельності відповідає на іншу загрозу, ніж
   частота: не «надто часто», а «надто багато одночасно» - саме це вичерпує
   пам'ять перед memory-hard хешем.
4. **Коштувати однаково в обох гілках.** Гілка «немає такого акаунта» мусить
   витратити стільки ж роботи хешування, скільки «невірний пароль», інакше час
   відповіді зчитує таблицю користувачів.

І крізь усе це - одне правило для помилок: кожна відмова - той самий статус із
тим самим машинним слагом, тож фронтенд може діяти на нього, а зловмисник не
дізнається з нього нічого.

## Приклад A - падати на старті

`env` заповнює конфіг із тегів; `Validate` перевіряє те, чого теги не можуть.
Ключовий рядок - `jwt.CheckKey`, те саме правило, яке `Sign` і `Verify`
застосовують на кожен виклик, експортоване саме для того, щоб конфігурація
падала першою:

```go
func (c *Config) Validate() error {
	if err := jwt.CheckKey([]byte(c.JWTSecret)); err != nil {
		return fmt.Errorf("JWT_SECRET is unusable: %w", err)
	}
	// ... крос-польові перевірки ...
	return nil
}
```

`TokenManager.Check` - та сама ідея для менеджера: «чи вміє він взагалі
підписувати й перевіряти», спитано на старті без карбування токена. Разом вони
перетворюють «перший вхід падає в продакшні» на «процес відмовляється
стартувати».

## Приклад B - два гальма, дві загрози

Обмеження частоти й тротл виглядають схоже й відповідають на протилежні питання.
Навішені на групу auth, тож решта API не гальмується:

```go
r.Route("/auth", func(g *mux.Router) {
	g.Use(middlewares.RateLimit(middlewares.RateLimitConfig{
		Limit:  cfg.AuthAttempts, // напр. 10 спроб...
		Window: cfg.AuthWindow,   // ...за 15 хвилин, на адресу клієнта
	}))
	g.Use(middlewares.Throttle(cfg.AuthConcurrency, // не більше N одночасно
		middlewares.WithThrottleRetryAfter(2)))
	g.Post("/signin", s.signIn)
})
```

`RateLimit` - це «як часто один клієнт може повертатися». `Throttle` - «скільки
цієї роботи вміщається в процес одночасно». Десять за хвилину все одно пропускає
десять в одну мить; десять слотів - ні. Перед входом доречні обидва - і
`RateLimit` за замовчуванням падає **закрито**, тож збій стора відхиляє запити, а
не тихо знімає ліміт із вашого маршруту входу.

## Приклад C - бюджет пам'яті

Хешер живе за семафором, а семафор - навколо операції, не на маршруті:

```go
func (s *service) verify(encoded string, password []byte) error {
	s.guard <- struct{}{}          // один із фіксованого числа слотів
	defer func() { <-s.guard }()
	return s.hasher.Verify(encoded, password)
}
```

Пам'ять належить процесу, не якомусь одному ендпоінту: хешер досяжний і з входу,
і зі зміни пароля, і з адмінських скидань, тож бюджет, що жив би на маршруті,
можна перевищити, зайшовши іншим. Правило розміру - єдине число, яке треба
пам'ятати: **вартість на хеш помножена на паралельність мусить вміститися в
бюджет пам'яті процесу.** На дефолті Argon2id у 64 МіБ вісім слотів - це пів
гігабайта. Хешер свідомо не тротлить себе - він не знає вашого бюджету - тому
семафор ставити вам.

## Приклад D - однакова вартість для відсутнього акаунта

`auth.BurnVerify` витрачає справжню перевірку проти decoy-хеша на гілці, де
користувача немає:

```go
stored, ok := s.users[email]
if !ok {
	auth.BurnVerify(s.hasher, s.decoy, []byte(password)) // та сама робота, без юзера
	// ...відповісти тим самим 401 із тим самим слагом, що й невірний пароль
	return
}
```

Decoy - справжній хеш чого завгодно, збудований раз на старті тим самим хешером
із тими самими налаштуваннями. Без цього «немає акаунта» відповідає за
мілісекунду, а «невірний пароль» - за сто, і секундомір зчитує, які адреси
зареєстровані - попри однакові тексти помилок. Він вирівнює рівно цю різницю й
нічого більше: обмеження частоти й однакові відповіді все ще ваші (вони - вище).

## Приклад E - тест підключення

Це той тест, про який розділ насправді, і це тиха наполегливість патерну:
**довести, що захист підключено, а не лише написано.** Зелений юніт-тест на
`RateLimit` каже, що middleware працює. Він нічого не каже про те, чи хтось
навісив його на маршрут. Тож тест ганяє реальний роутер і стверджує, що гальмо
кусає:

```go
// Четверта спроба з однієї адреси, бюджет три, має бути 429.
var got429 bool
for i := 0; i < cfg.AuthAttempts+2; i++ {
	if post(h, addr, body).Code == http.StatusTooManyRequests {
		got429 = true
		break
	}
}
if !got429 {
	t.Fatal("the rate limit is not attached to /auth: ...")
}
```

Ключова деталь: закоментуйте `g.Use(middlewares.RateLimit(...))` у роутері - і
цей тест падає. Тест, чийого падіння ніхто не бачив, вартий не більше за мертвий
код, який він охороняє.

```

   wrong password:  401 {"code":401,"error":"invalid_credentials","message":"Invalid credentials"}
```

## Що ви дізналися

- Валідуйте конфігурацію на старті й перевіряйте ключ підпису через
  `jwt.CheckKey` (і `TokenManager.Check`), щоб поганий секрет спиняв деплой, а не
  перший вхід.
- `middlewares.RateLimit` (fail-closed) і `middlewares.Throttle` відповідають на
  різні загрози - частоту й паралельність - і ендпоінт входу хоче обидва.
- Обмежуйте паралельність Argon2id семафором навколо операції, з розміром так,
  щоб вартість-на-хеш × паралельність вмістилася в процес; хешер не зробить
  цього за вас.
- `auth.BurnVerify` коштує гілку відсутнього акаунта як невірний пароль, тож
  таймінг не зливає таблицю користувачів.
- Відповідайте на кожну відмову тим самим статусом і слагом
  (`resp.WithErrorSlug`) і тестуйте, що гальма справді підключені - захист, який
  ніхто не навісив, не захист.

Далі: що відбувається після входу - оновлення сесії без того, щоб віддати
зловмиснику ключ.
