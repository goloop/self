# 13. За зворотним проксі

**Задача.** Випустити службу, що стоїть за nginx, балансувальником чи CDN - а це
майже кожна служба - без тихої пастки, що з цим приходить. Для Go-процесу запит
за проксі надходить *від проксі*, тож `r.RemoteAddr` - адреса проксі, та сама для
кожного відвідувача. Усе, що ключується адресою клієнта, це успадковує: ліміт
на IP стає одним спільним дозволом на весь загал, аудит-лог звинувачує проксі в
усьому, банліст банить усіх або нікого. Ніщо не падає. Воно просто тихо
перестає бути по-клієнтським - і лише в продакшні, бо розробник, що б'є напряму,
ніколи не йде через проксі.

**Модулі.** [`middlewares`](https://github.com/goloop/middlewares) резолвить
справжній IP клієнта (`RealIP`), ключує ліміт за ним (`KeyByIP`) і несе
запитовий логер (`WithContextLogger` / `LoggerFrom`);
[`mux`](https://github.com/goloop/mux) і
[`resp`](https://github.com/goloop/resp) доповнюють обробник.

**Рецепт.** [`recipes/013-reverse-proxy`](../recipes/013-reverse-proxy/)

## Пастка й чому фікс під охороною

Справжня адреса клієнта - у пересланому заголовку `X-Forwarded-For`, який ставить
проксі. Але заголовок - не доказ: хто завгодно може надіслати
`X-Forwarded-For: 1.2.3.4` і видати себе за іншого. Тож `RealIP` вірить
заголовку **лише** від пірів, яких ви оголосили довіреними, і в іншому разі
довіряє прямому з'єднанню. Це робить безпечний дефолт - не довіряти нічому - і
тим, який тихо ділить одне відро на всіх, щойно з'являється проксі, поки ви його
не назвете.

## Приклад A - колапс

Без політики довірених проксі два клієнти за одним проксі резолвляться в адресу
проксі, тож ділять ключ ліміту:

```go
r.Use(middlewares.RealIP()) // без довірених проксі

// за nginx обидва запити мають RemoteAddr = проксі:
//   client 203.0.113.1 -> key 127.0.0.1
//   client 203.0.113.2 -> key 127.0.0.1   <- ТОЙ САМИЙ ключ
```

Одне відро на весь загал. Ліміт «двадцять спроб на адресу» тепер двадцять на
всіх, і другий, хто помилився з паролем, блокується першим.

## Приклад B - фікс

`WithTrustedProxies` називає підмережу проксі. Тепер пересланому заголовку
вірять від неї, і два клієнти знову отримують окремі ключі:

```go
r.Use(middlewares.RealIP(
	middlewares.WithTrustedProxies("127.0.0.0/8"))) // підмережа вашого проксі

//   client 203.0.113.1 -> key 203.0.113.1
//   client 203.0.113.2 -> key 203.0.113.2   <- знову окремі
```

У реальному деплої `127.0.0.0/8` - це nginx на тому ж хості; використайте
діапазон вашого балансувальника чи опубліковані діапазони вашого CDN.

## Приклад C - підробці не вірять

Клієнт, що з'єднується напряму - без довіреного проксі попереду - і підробляє
заголовок, усе одно резолвиться у свою справжню адресу:

```go
// пір 203.0.113.9 (не в довіреному діапазоні), заголовок заявляє 10.0.0.1:
//   resolved to 203.0.113.9  <- справжній пір, не брехня
```

Саме тому дефолт безпечний: резолвлена адреса надійна саме тому, що вірить
заголовкам лише від пірів, за яких ви поручились.

## Приклад D - `RemoteAddr` лишається недоторканим

Це деталь, яку реальний проєкт зрозумів хибно, тож вона заслуговує окремого
прикладу. `RealIP` пише резолвлену адресу в **контекст запиту** - і більше
нікуди. Він ніколи не переписує `r.RemoteAddr`:

```go
middlewares.RealIPFrom(r.Context()) // "203.0.113.1" - клієнт
r.RemoteAddr                        // "127.0.0.1:9999" - усе ще проксі
```

Питайте `RealIPFrom` про адресу клієнта. Код, що читає `r.RemoteAddr`, вірячи,
що middleware його нормалізував, буде ключувати на проксі - це той самий колапс
із прикладу A, випущений проєктом, чий коментар казав «RealIP нормалізував
RemoteAddr», тоді як код такого не робив.

## Приклад E - логи, що корелюються

`Logger` пише один рядок на запит із його id. `WithContextLogger` кладе в
контекст запитовий логер - що вже несе `request_id`, `method`, `path` і
резолвлений `remote_ip` - тож власні рядки логу обробника зчіплюються із
запитом, без того, щоб хтось руками протягував ідентифікатори:

```go
r.Use(middlewares.Logger(middlewares.WithContextLogger()))

// у хендлері:
middlewares.LoggerFrom(r.Context()).Warn("upstream slow", "ms", 512)
// -> {"msg":"upstream slow","ms":512,"request_id":"...","remote_ip":"203.0.113.7",...}
```

Альтернатива - пам'ятати додавати id на кожному місці виклику, що падає тихо й
вибірково: рядки без нього - це ті, що написані поспіхом, а це ті, що написані
під час інциденту.

## Звіт про виконання

```
$ go run .
A. behind a proxy, WITHOUT a trusted-proxy policy:
   client 203.0.113.1 -> key 127.0.0.1
   client 203.0.113.2 -> key 127.0.0.1
   ^ SAME key: one rate-limit bucket for the whole userbase
B. WITH WithTrustedProxies("127.0.0.0/8"):
   client 203.0.113.1 -> key 203.0.113.1
   client 203.0.113.2 -> key 203.0.113.2
   ^ separate keys: the limit is per client again
C. a client forging X-Forwarded-For with no trusted proxy in front:
   claimed 10.0.0.1, resolved to 203.0.113.9 (the real peer, not the lie)
D. RealIP leaves r.RemoteAddr untouched:
   RealIPFrom(ctx) = 203.0.113.1   r.RemoteAddr = 127.0.0.1:9999
   ask RealIPFrom for the client; RemoteAddr is still the proxy
E. a handler's logs correlate with the request:
   handler log: msg="upstream slow" remote_ip=203.0.113.7 request_id set=true
```

## Що ви дізналися

- За проксі `r.RemoteAddr` - це проксі для кожного відвідувача; усе, що
  ключується ним, тихо стає спільним.
- `middlewares.RealIP` резолвить справжню адресу клієнта, але вірить пересланому
  заголовку лише від пірів `WithTrustedProxies` - заголовок, який хто завгодно
  підробить, не доказ.
- Безпечний дефолт (не довіряти нічому) правильний лише коли ви назвали свій
  проксі; ставте `WithTrustedProxies` на його справжню підмережу в кожному
  проксованому деплої.
- `RealIP` пише лише контекст. Питайте `RealIPFrom(ctx)`, ніколи `r.RemoteAddr`.
- `WithContextLogger` + `LoggerFrom` корелюють логи обробника із запитом за
  замовчуванням, а не за пам'яттю кожного.
