# 12. Життєвий цикл refresh-токена

**Задача.** Тримати користувача залогіненим, не лишаючи довговічного облікового
запису напризволяще. Access-токен короткочасний за задумом; refresh-токен - те,
чим клієнт тихо отримує наступний. Це робить refresh-токен цінним для крадіжки,
тож увесь цикл крутиться навколо одного питання: коли повертається токен, який
уже не чинний, - це чесний клієнт повторює запит, чиєї відповіді не отримав, чи
зловмисник відтворює вкрадений токен?

**Модулі.** [`auth`](https://github.com/goloop/auth) визначає життєвий цикл
refresh-токена - ротацію, виявлення повторного використання, grace-вікно, строк
дії та «вийти всюди» - а [`auth/authtest`](https://github.com/goloop/auth)
доводить, що будь-який стор реалізує контракт правильно, включно з паралельністю.

**Рецепт.** [`recipes/012-refresh-lifecycle`](../recipes/012-refresh-lifecycle/)

## Одне правило

Кожен refresh **ротує**: видає новий токен і виводить із обігу старий.
Пред'явлення виведеного токена - отже, сигнал, і те, як ви його читаєте, і є вся
безпека схеми:

| Пред'явлений токен | Статус | Що означає | Відповідь |
|---|---|---|---|
| чинний | `Rotated` | чесний refresh | нова пара токенів |
| щойно зротований, у вікні | `PreviousWithinGrace` | втрачена відповідь, не крадіжка | `401`, **не** відкликати |
| давніший чи вже відкликаний | `ReusedStale` | відтворений токен | відкликати всю родину |
| поза строком дії | `ErrRefreshExpired` | лінивий клієнт | `401`; не повторне використання |

Правило, що все зв'язує: повторне використання виведеного токена означає, що
родина токенів скомпрометована, тож завершіть її. Усе інше - або чесний refresh,
або чесна помилка, і не має виганяти користувача з інших пристроїв.

## Приклад A - ротація

`RotateWithStatus` міняє пред'явлений токен на наступника й звітує, чим була
спроба:

```go
next, _, _ := auth.NewRefreshToken(subject, ttl)
res, err := auth.RotateWithStatus(ctx, store, presentedID, next)
// res.Status == auth.Rotated, err == nil: віддайте `next` клієнту
```

## Приклад B - виявити повторне використання

Той самий токен, пред'явлений після ротації, - це сигнал крадіжки. Відповідь -
не 401, а відкликання кожної сесії суб'єкта, тож вкрадений і легітимний токени
обидва помирають, і користувач входить знову:

```go
res, err := auth.RotateWithStatus(ctx, store, oldID, next)
if res.Status == auth.ReusedStale {
	auth.RevokeAll(ctx, store, subject) // завершити всю родину
}
```

Зауваження, з яким рецепт обережний: `RotateResult.Subject` заповнюється там, де
стор ще може назвати власника, але stale-токен, чий запис давно зник, не завжди
може. Реальний обробник `/refresh` уже завантажив запис і перевірив секрет до
ротації, тож знає суб'єкта з того кроку - тримайте його там, а не покладайтеся на
результат.

## Приклад C - grace-вікно

Клієнт, чиє з'єднання обірвалось, ніколи не бачив виданого наступника й повторює
токен, який досі тримає, - той, що зротований мить тому. Це не крадіжка, і
карати за це - виганяти чесних користувачів. `auth.WithGrace` відкриває коротке
вікно, у якому безпосередньо попередній токен - `PreviousWithinGrace`, а не
`ReusedStale`:

```go
store := auth.NewMemoryRefreshStore(auth.WithGrace(10 * time.Second))
// ...повтор щойно зротованого токена протягом 10с:
// res.Status == auth.PreviousWithinGrace -> відповісти 401, НЕ відкликати
```

Тримайте вікно коротким. Кожна його секунда - секунда, у яку вкрадений токен
теж прийняли б один раз - і воно приймає лише *безпосередньо* попередній токен,
ніколи той, що на дві ротації назад, який може бути тільки повтором.

## Приклад D - строк дії - це не повторне використання

Токен поза строком дії відхиляється, але відмова - це `ErrRefreshExpired`, а не
сигнал повторного використання. Ця різниця несуча: лінивий клієнт, чий токен
просто застарів, - не зловмисник, і відповідь `ErrRefreshUsed` відкликала б його
інші сесії за провину бути відсутнім:

```go
_, err := auth.RotateWithStatus(ctx, store, expiredID, next)
errors.Is(err, auth.ErrRefreshExpired) // true
errors.Is(err, auth.ErrRefreshUsed)    // false - не відкликати родину
```

## Приклад E - conformance-тест

Рецепт зберігає токени в `auth.NewMemoryRefreshStore`, тож працює без жодної
інфраструктури. Продакшн-служба ставить це за Redis чи Postgres - і саме там
живуть тонкі баги: неатомарна ротація дає двом клієнтам обом отримати
наступника; індекс, оновлюваний у `Save` і `Revoke`, але не в `Rotate`, лишає
«вийти всюди» зі звітом про успіх, поки сесія жива.

`auth/authtest` тримає будь-який стор до всього контракту, включно з
паралельністю:

```go
func TestRedisStore(t *testing.T) {
	authtest.RefreshStore(t, func(t *testing.T) auth.RefreshStore {
		return newRedisStore(t) // свіжий, порожній
	})
}
```

Він знайшов реальний баг в еталонному сторі на першому ж прогоні. Напишіть свій
Redis- чи Postgres-стор, наведіть це на нього - і той самий набір доведе, що він
дотримується тих самих правил, включно з тими, що проходять один послідовний
тест і падають під навантаженням.

## Спільний стор, коротко

Еталонний memory-стор однопроцесний. Продакшн-форма - у
[довіднику `auth`](https://github.com/goloop/auth) під «Writing a shared store»;
єдиний інваріант, який треба забрати, - ротація мусить бути **атомарною**. У
Redis це скрипт, а не послідовність команд, і `del` - це водночас і перевірка, і
заявка:

```lua
if redis.call('del', KEYS[1]) == 1 then   -- хто видалив ключ, той і виграв
  redis.call('set', KEYS[2], ARGV[1], 'EX', ARGV[4])  -- зберегти наступника
  -- ...тут же підтримати індекс суб'єкта...
  return 1
end
return 0                                    -- хтось уже зротував його
```

`get`, потім `del` двома командами лишає вікно, у якому перевірку проходять обоє
- саме цю гонку атомарна ротація закриває.

## Звіт про виконання

```
$ go run .
A. a normal refresh issues the next token:
   status=rotated  a successor was issued
B. replaying the retired token is a theft signal:
   status=reused_stale  err=auth: refresh token already used
   -> RevokeAll("ada"): the whole family is revoked
C. a grace window absorbs a dropped response:
   replaying the just-rotated token: status=previous_within_grace
   -> answer 401, but do NOT revoke: this is a lost response, not theft
D. an expired token is refused, but is not reuse:
   err is ErrRefreshExpired: true (and NOT ErrRefreshUsed: false)
E. sign out everywhere:
   -> every one of dave's refresh tokens is now revoked
```

## Що ви дізналися

- Кожен refresh ротує; виведений токен, що повертається, - сигнал, читаний через
  `RotateWithStatus`.
- `ReusedStale` означає, що родина скомпрометована - відповідайте `RevokeAll`, а
  не голим 401.
- Grace-вікно (`auth.WithGrace`) відрізняє втрачену відповідь від повтору, тож
  чесних клієнтів не виганяє; тримайте його коротким, і воно покриває лише
  безпосередньо попередній токен.
- Строк дії - це `ErrRefreshExpired`, ніколи не повторне використання - лінивий
  клієнт не злодій.
- Зберігайте токени де хочете, але доводьте стор через `auth/authtest`: ротація
  мусить бути атомарною, а індекс суб'єкта - підтримуватись у `Save`, `Rotate` і
  `Revoke` однаково.
